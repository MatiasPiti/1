Compilar es lo unico que tarda (30-45 min). Se puede hacer

El OtterActualizador busca las apps nuevas AL LADO DE SI

    - la carpeta  dist\  ENTERA
    - la carpeta  scripts\  (para el blindaje del PASO 6)

>>> SI PROBASTE LOS .exe DESDE dist\ ANTES DE COPIAR <<<
Cada app se crea ahi su config.ini, database\, logs\ y
tickets\ de prueba. Borralos antes de copiar al pendrive:

    Get-ChildItem dist -Directory | ForEach-Object {
        foreach ($d in "database","logs","tickets","backups","SYNC_DATA") {
            $r = Join-Path $_.FullName $d
            if (Test-Path $r) { Remove-Item $r -Recurse -Force }
        }
        $c = Join-Path $_.FullName "config.ini"
        if (Test-Path $c) { Remove-Item $c -Force }
    }

O mas simple: borrar dist\ entera y volver a compilar sin
abrir ningun .exe.

(El Actualizador ya filtra estos datos y conserva los del
cliente, pero no le des trabajo de mas.)

SI COMPILASTE EN CASA: en el local salteate el PASO 1 y el
PASO 3, y en el PASO 4 corre el OtterActualizador DESDE EL
PENDRIVE.

 PASO 5 - ARRANCAR EL SERVICIO
===========================================================
*************************************************
*** ESTE ES EL PASO QUE SE OLVIDO LAS DOS     ***
*** VECES QUE SE CAYO EL DUENO REMOTO.        ***
*** NO SALTEARLO.                             ***
*************************************************

Por que: el Actualizador relanza el servicio SOLO si estaba
corriendo antes de actualizar. Como lo paramos en el PASO 2,
nunca lo va a arrancar. Hay que hacerlo a mano.

    Start-Service SistemaDualStockService
    Start-Sleep -Seconds 8
    Get-Service SistemaDualStockService
    netstat -ano | findstr 8765

Tiene que pasar LAS DOS COSAS:
    [ ] Status = Running
    [ ] una linea con LISTENING

Si falta el LISTENING: PARAR ACA y avisar. Significa que el
servicio arranco pero la API remota no levanto, que es
justo el caso que Leo ve como "no me puedo conectar".

===========================================================
 PASO 6 - CORRER EL BLINDAJE
===========================================================
    powershell -ExecutionPolicy Bypass -File .\scripts\blindar_local.ps1

Se corre UNA sola vez. Hace 5 cosas:

  0. Guarda el estado actual en
     C:\SistemaDual\watchdog\estado_antes_del_blindaje.txt
  1. El servicio arranca con Windows y se reintenta solo.
  2. La PC no se suspende mas (ni enchufada ni a bateria).
  3. Instala un watchdog que cada 5 minutos revisa EL
     PUERTO (no solo si el servicio dice "Running": la API
     remota puede no haber levantado con el servicio
     corriendo, y ese es el caso que no se ve). Si esta
     muerto, lo reinicia. Se planta despues de 3 reinicios
     en 24 hs.
  4. Deja Tailscale en modo "unattended" - sin esto,
     Tailscale se desconecta al cerrar la sesion de
     Windows.

NO toca la base ni el config.ini.

AL FINAL IMPRIME UNA TABLA. Las 5 filas tienen que decir SI:

    [ ] Servicio en Automatic
    [ ] Watchdog instalado        (Estado=Ready)
    [ ] Tailscale unattended
    [ ] Servicio corriendo
    [ ] Puerto 8765 escuchando

Si "Tailscale unattended" dice NO, hacerlo a mano:
    icono de Tailscale (al lado del reloj) -> Preferences
    -> "Run unattended". Es el punto mas importante de todos.

Si alguna otra dice NO: mandar la tabla mas el archivo
estado_antes_del_blindaje.txt


===========================================================
 PASO 7 - LA PRUEBA DE VERDAD
===========================================================
CERRAR SESION en la PC del local. NO APAGAR.
(Inicio -> el usuario -> "Cerrar sesion")

Despues, desde el celular con Tailscale conectado, abrir en
el navegador:

    http://IP-DEL-LOCAL:8765/health

Si contesta CUALQUIER COSA -aunque diga "token invalido"-
esta VIVO. El navegador no manda el token, por eso rechaza:
que rechace ya prueba que hay alguien escuchando.

Si no carga nada: el servicio esta caido. Volver al PASO 5.

Esto es exactamente lo que fallaba antes al cerrar sesion.

===========================================================
    dir C:\SistemaDual\backups

Si a las 24 horas no aparece ninguno, el servicio no esta

===========================================================
 OPCIONAL (recomendado) - PROBAR EL CARTEL DE BASE DANADA
===========================================================
Esto nunca se probo en Windows real.

HACERLO EN EL USB DE EMERGENCIA, NUNCA EN LA PC DEL LOCAL.
El USB tiene base propia, asi que no hay ningun riesgo.

  1. Abrir USB_Caja.exe una vez y cerrarlo (para que se
     cree la base).
  2. Abrir database\stock.db con el Bloc de notas, escribir
     cualquier cosa, guardar.
  3. Volver a abrir USB_Caja.exe.

Tiene que aparecer un cartel diciendo que la base esta
danada y ofreciendo restaurar la copia.

Antes de este cambio no pasaba absolutamente nada: el .exe
moria en silencio, sin cartel y sin archivo.


===========================================================
 SI ALGO SALE MAL - DIAGNOSTICO EN 2 PASOS
===========================================================
(se puede hacer entero desde el celular)

1. App de Tailscale: el nodo del local, esta ONLINE?
      NO -> la PC esta dormida o Tailscale se cayo ahi.
            No se arregla en remoto.
      SI -> seguir al 2.

2. Navegador: http://IP-DEL-LOCAL:8765/health
      Contesta algo -> el servicio esta VIVO, el problema
                       es del lado del Dueno Remoto.
      No carga nada -> el servicio esta caido.

Desde una PC el equivalente es:
    Test-NetConnection IP-DEL-LOCAL -Port 8765

    PingSucceeded True + TcpTestSucceeded False
    = la red llega, no hay nada escuchando.

 COMANDOS UTILES
===========================================================
